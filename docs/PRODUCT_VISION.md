# Product vision

Current direction and standing permission: [authorisation and design gate](AUTHORIZATION.md). UI development is paused for the user-requested design decision; historical observations and test results retain their original dates.

Fire Take Off is a private, independently implemented fire protection estimating and automated takeoff platform. The current objective (2026-10-29) is competitive Countfire functionality with a distinctive premium modern design: precision, productivity and clarity before decoration. The earlier copied-interface objective is superseded. The initial user is a single estimator using a private application on macOS. Complete functional workflow scope, including publicly documented collaboration and integrations, remains in the backlog.

Development is paused at the user's explicit design checkpoint. [Research, three concepts and the proposed design system](design/PHASE_1_UI_UX_RESEARCH.md) must be discussed and approved before implementation. Graphite/white/amber is a preferred direction under evaluation, not an accepted production design. No architecture, calculation policy or feature completion is established by these wireframes.

The core workflow is: create a project, organise drawing sets and disciplines, review high-resolution PDFs, select and count symbols across drawings/floors, inspect and correct results, calibrate and measure, divide quantities into zones, handle overlays/revisions, produce auditable schedules and Excel outputs, then price and export estimates.

Required trades include sprinkler, hydrant, electrical, mechanical and general construction. A trade being requested does not establish that Countfire has a dedicated module for it. Track evidence and unknowns separately. Include notes, coverage visualisation, Smart Select, connected measures and fittings, floorplans, specification comparison, libraries/kits, margins and preliminaries where public evidence supports them.

Current user-directed exception (2026-10-28): do not build or clone the catalogue section yet. Tyrone will customise it later. Keep catalogue UI/product-library management and catalogue-dependent imports or kit management deferred; continue independent takeoff and estimating work. Do not treat full-parity scope as permission to implement the deferred catalogue.

Success requires reliable workflows on representative authorised construction drawings, durable project recovery, traceable manual corrections, tested numerical accuracy and reproducible acceptance evidence per feature. A plausible interface, a single successful drawing or a marketing assertion is insufficient.

Scope boundaries: Phase 0 establishes memory, research inventory, architecture evaluation and REA verification. No product build begins until its gate passes. No unrelated products or AI designer features. All branding, code and fixture assets must be original or appropriately licensed. Learn from public documentation and the supplied authorised account. Standing user permission is recorded in AUTHORIZATION.md; no third-party source licence is recorded. Do not circumvent access controls.

Public research is a baseline dated 2026-10-22, not a claim of exhaustive parity. Phase 1 must resolve unknowns, specify each workflow and freeze a dated reference baseline. Future Countfire changes enter the parity backlog explicitly.

Historical UI/UX sequencing recommendation, 2026-10-28: continue reference matching while workflows mature. Superseded by Tyrone's explicit 2026-10-29 request to stop development for research and design approval now. Catalogue customisation remains deferred.
